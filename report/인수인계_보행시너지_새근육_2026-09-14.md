## 0. 한 줄 요약과 현재 결정

**사람 다리 근육 80개가 하던 일을, 다리당 새 근육 8개로 대신하게 만드는 중이다.** 시뮬레이션에서 그 8개만으로 사람 걸음을 그대로 재현하는 것까지 됐다.

지금까지 정해진 것:

| 항목 | 결정 | 근거 |
| --- | --- | --- |
| 다리당 새 근육 수 | **8개** | 5개는 무릎 토크를 못 낸다(§5, §6). 8개는 7명의 걸음을 전부 낸다(§7) |
| 로봇 다리가 움직이는 방향(자유도) | **4개**: 고관절 앞뒤·옆, 무릎, 발목 | 나머지(고관절 회전, 발 내번, 발가락)는 걷기 토크가 작아 수동으로 둠(§9) |
| 로봇 몸 크기 | **피험자3 그대로 (63.5 kg, 1.69 m)** | 그 몸으로 만든 모델·데이터가 전부 있어 다시 만들 게 없음(§9) |
| 근육 부착 위치·경로 | 우리에게 유리하게 자유 | 무릎을 넘어가는 경로도 허용 |
| 액추에이터 | KIMM 모듈 사양(초대형 1,000~5,000 N 등) | 발목 피크 89 Nm ÷ 모멘트암 5 cm ≈ 1,800 N, 초대형 1개 범위 |

어디까지 됐나 (9/15 기준): **사람 데이터 → 근육 8개 방향 → 케이블 경로 → 시뮬레이션 걸음·스쿼트 재현**의 사슬이 처음부터 끝까지 통과했다. 방향은 사람 근육 계산(SO)에 기대지 않고 관절 토크에서 직접 최적화했고(§10-A, 9/15에 걷기+스쿼트 기준으로 다시 설계), 그 방향을 케이블 경로로 구현해(§10-D, 9/15에 2단계 미세조정 추가) 걷기 6걸음과 스쿼트를 오차 10 % 이하로 재현했다. 남은 큰 일은 세 가지 — 뼈를 뚫지 않는 경로(경로 3차), 로봇이 스스로 균형 잡고 걷기(접촉 모델 + 제어기), 인공근육 모듈의 측정값 반영(§10-E).

추가 결정(9/14, 9/15 수정): 동작 범위 = **걷기 + 스쿼트**(점프 제외). 앉았다 서기는 뺐다 — 논문 팀 데이터에 의자가 받치는 힘이 없어 앉아 있는 구간의 관절 토크가 틀리고, 의자 힘이 없는 구간은 스쿼트와 운동학이 같아 새 정보가 없다(§13-27). 용량 여유 10 %.

## 1. 목표를 풀어 쓰면

사람 다리에는 근육이 약 40개씩(양다리 80개) 있다. 로봇에 그걸 다 달 수는 없다. 그래서 질문은 이렇다.

> **"사람이 걸을 때 쓰는 근육 활동을 몇 개의 묶음으로 줄일 수 있고, 그 묶음 하나를 인공근육 하나로 만들면 로봇이 걸을 수 있나?"**

이걸 답하려면 (1) 사람이 걸을 때 관절에 얼마의 힘(토크)이 필요한지, (2) 그 토크를 사람 근육이 어떻게 나눠 내는지, (3) 그 나눔에 반복되는 패턴(시너지)이 몇 개인지, (4) 그 패턴대로 새 근육을 만들면 정말 걷는지를 차례로 계산해야 한다. 이 문서의 §3~§7이 그 순서다.

## 2. 용어 사전 (이것만 알면 아래를 읽을 수 있다)

| 용어 | 뜻 |
| --- | --- |
| **OpenSim** | 스탠퍼드에서 만든 근골격 시뮬레이터. 사람 뼈대·근육 모델에 측정한 움직임을 넣어 힘을 계산한다. 우리는 4.6 버전, 파이썬으로 부른다. |
| **모델(.osim)** | 사람 한 명의 뼈 길이·질량·근육 80개를 담은 파일. 피험자마다 하나. |
| **운동학 / IK** | 관절 각도의 시간 변화. IK(Inverse Kinematics)는 마커 위치에서 관절 각도를 푸는 것. 우리는 이미 풀린 각도를 받았다(`*_ik.mot`). |
| **지면반력 / GRF** | 발이 바닥을 밟을 때 바닥이 발을 미는 힘. 힘판으로 잰다(`*_grf.mot`). |
| **역동역학 / ID** | 관절 각도 + 지면반력에서 **관절 토크**를 계산하는 것(Inverse Dynamics). 결과 예: "발목은 이 순간 89 Nm를 내야 한다." **이 값이 근육 설계의 진짜 기준이다.** |
| **잔차 (residual)** | ID를 풀 때 계산이 안 맞는 만큼 골반에 가짜 힘을 넣어 맞추는데, 그 가짜 힘. 작을수록 데이터가 물리적으로 정합. 우리 기준: 지면반력 피크의 5 % 미만. |
| **모멘트암** | 근육이 관절을 돌리는 지렛대 길이(m). 근육 힘 × 모멘트암 = 관절 토크. |
| **정적 최적화 / SO** | 관절 토크가 주어졌을 때 "근육 80개가 각각 얼마나 힘을 냈나"를 추정하는 것(Static Optimization). 정답이 없어서 "총 활성도 제곱합 최소"라는 가정으로 푼다. **가정이라서 실제 근육과 다를 수 있다**(§8에서 확인됨). |
| **활성도** | 근육이 켜진 정도 0~1. SO의 출력. |
| **보조 액추에이터 (reserve)** | SO나 시뮬레이션에서 근육이 못 낸 토크를 대신 내는 가상의 모터. 이게 크면 "근육만으론 안 된다"는 뜻. 결과는 "ID 피크의 몇 %"로 표시한다. |
| **근육 시너지 / NMF** | 근육 활성도 행렬(시간 × 근육)을 "패턴 k개 × 시간 가중치"로 분해하는 것. NMF(비음수 행렬분해)로 푼다. 패턴 하나 = "이 근육들이 이 비율로 같이 켜진다" = 시너지. |
| **VAF** | 시너지 k개로 원래 활성도를 얼마나 설명하나(%). 90 % 넘는 최소 k를 고른다. |
| **global / dual 기준** | global: 전체 VAF ≥ 90 %. dual: 거기에 더해 근육 하나하나도 ≥ 75 %. dual이 더 엄격해서 k가 커진다. |
| **자유도 / DOF** | 관절이 움직이는 방향 수. 다리 하나에 모델상 7개(§9 표). |
| **양의 생성 (positive spanning)** | 인공근육은 **당기기만** 한다(밀지 못함). 그래서 어떤 방향의 토크든 "당기는 근육들의 양의 조합"으로 낼 수 있어야 한다. n개 방향을 다 덮으려면 근육이 최소 n+1개. |
| **MocoInverse** | OpenSim의 최적제어 도구. "이 걸음(각도·지면반력 고정)을 내려면 근육 신호가 어때야 하나"를 시간 전체에 걸쳐 한 번에 푼다. SO보다 무겁지만 동역학이 다 들어간다. |
| **EMG** | 근전도. 피부 전극으로 잰 실제 근육 활동. SO 추정치의 정답지 역할. |
| **walking / walkingTS** | 평지 걷기 / 몸통을 좌우로 흔들며 걷기(trunk sway). 무릎 부하를 바꾸는 실험 조건. |

## 4. 파이프라인 — 사람 근육 80개까지

한 걸음(trial)마다 이 순서로 돈다. `run.sh` 또는 `batch.py`가 전부 자동으로 한다.

```
.b3d → (변환) → ik.mot, grf.mot, 모델.osim
        ↓ run_trial.py             역동역학 ID        → 관절 토크 (Nm)          ← 설계의 진짜 기준
        ↓ run_muscle_analysis.py   근육 분석          → 모멘트암, 근육 길이
        ↓ run_static_optimization.py  정적 최적화 SO   → 근육 80개 활성도·힘      ← 가정 섞임
        ↓ synergy.py               NMF               → 시너지 k개 (W: 구성, C: 시간)
```

**결과 (7명 42걸음, 좌우 따로 → 84개 분해)**
- global 기준(전체 VAF 90 %)으로 **k = 5**가 84개 중 56개에서 최소. 이게 "사람 걸음의 시너지는 5개"라는 결과다.
- dual 기준으로는 약 8. 하지만 이건 SO가 비슷한 근육들(예: 비복근 안쪽·바깥쪽) 사이에서 힘을 임의로 나누는 탓에 근육별 VAF가 떨어져서 커지는 것이므로, **8은 "SO가 임의적"이라는 진단이지 시너지 수가 아니다.**
- walking과 walkingTS는 시너지 수가 같다. walkingTS는 몸통만 흔드는 조건이라 다리 근육 패턴은 안 바뀐다(허리 굽힘 각이 24° → 47°로 커진 것을 데이터에서 확인).

## 5. "시너지 5개 → 새 근육 5개"는 왜 안 되나

처음 목표는 시너지 하나당 새 근육 하나, 즉 다리당 5개였다. 세 단계로 검사했고 전부 "안 된다"였다.

**(1) 이론.** 인공근육은 당기기만 하므로 n개 방향을 덮으려면 최소 n+1개. 다리 4자유도면 5개가 턱걸이, 6자유도면 7개.

**(2) 방향 검사** (`report/spanning_check.py`). 시너지 5개 각각이 관절에 내는 토크 방향(고관절 굴곡·내전, 무릎, 발목의 4차원 벡터)을 계산해 4차원을 양으로 덮는지 봤다. **12개 분해 중 1개만 통과.** 걷기에 쓰는 방향만 있고 반대 방향(예: 무릎 신전)이 빈다.

**(3) 준정적 검사** (`report/lumped_actuator_test.py`). 새 근육 k개의 토크 방향을 고정하고, 매 순간의 관절 토크를 "당김(u ≥ 0)"만으로 맞출 수 있는지 최소제곱(NNLS)으로 풀었다.

| 새 근육 수 | 토크 오차 (ID 피크 대비) |
| --- | --- |
| 5개 | 분해의 36 %에서 10 % 초과, 최악 32 % — 무릎이 빈다 |
| 8개 | 전부 1 % 미만 |

즉 **5는 제어 신호 수(사람이 쓰는 패턴 수), 8은 하드웨어 근육 수**다. 둘은 다른 질문의 답이고 둘 다 맞다.

그림: `report/lumped_actuator_test.csv`

## 6. 새 근육을 실제로 달아서 걷게 했다 (MocoInverse)

준정적 검사는 순간순간의 힘 균형만 본다. 진짜로 걷는지는 동역학 시뮬레이션이 필요하다. 두 방식으로 했다(`report/moco_synergy_inverse.py`, `report/moco_new_muscles.py`).

- **A. 사람 근육 80개를 두고, 신호 k개로만 조종** (SynergyController). "사람 근육을 k개 신호로 몰 수 있나"의 답.
- **B. 사람 근육을 전부 떼고, 새 근육 k개를 단다.** 새 근육 = "신호 하나에 고관절·무릎·발목 토크를 고정 비율로 내는 액추에이터"(토크형, 아직 부착 경로는 없음). "하드웨어 근육 k개면 되나"의 답. **우리 질문엔 B가 맞는 검사.**

걸음(각도)과 지면반력은 실측 그대로 고정하고, 근육이 못 내는 만큼은 보조 액추에이터가 낸다. 보조가 ID 피크의 10 % 미만이면 "재현"으로 본다. 피험자3 walking1 결과:

| | 새 근육 8개 | 새 근육 5개 |
| --- | --- | --- |
| A. 사람 근육 80개 + 신호 k개 | 보조 최악 22 % (무릎) | 85 % |
| **B. 새 근육 k개만** | **8 % → 재현** | 48 % (무릎) → 실패 |

- 신호 상한을 3배 → 10배로 풀어도 안 바뀐다 → 힘 용량이 아니라 **방향**의 문제.
- A가 B보다 나쁜 건 시너지 재구성 오차(VAF 90~96 %)에 근육 동역학(활성 지연, 힘-길이-속도)이 얹혀서다.

## 7. 근육 방향을 고정하고 다른 걸음도 걷게 했다 (교차 검증)

**(1) 보조 비용 가중치 1은 검사가 아니다.** 목적함수가 (신호 u)² + (보조 Nm)²라, 새 근육이 낼 수 있어도 u가 커지면 보조에 떠넘기는 게 싸다. 준정적으론 오차 0인데 Moco에선 22~26 %가 나오는 착시. → **보조 가중치를 100으로** 두면 정말 못 내는 몫만 남는다. 이후 모든 Moco는 이 설정.

## 10. 방향 설계와 경로 설계 — 무엇을 어떻게 했고, 다음은 무엇인가

이 장은 두 단계다. **방향 설계**(10-A): 새 근육 8개가 각각 네 관절에 어떤 비율로 토크를 낼지(방향)와 얼마까지 낼지(용량)를 관절 토크에서 직접 최적화했다. **경로 설계**(10-D): 그 방향을 피험자3 뼈대 위 케이블 경로로 바꾸고(1단계: 근육 하나씩 방향 맞추기, 2단계: 8개를 한꺼번에 미세조정), 케이블 근육으로 걸음과 스쿼트를 재현했다. 10-B는 지금 근육 모델에 무엇이 지정돼 있고 진짜 근육엔 무엇이 더 필요한지, 10-C는 경로 설계에 쓰인 기법 이름, 10-E는 다음 단계다.

**방향 설계 결과 요약 (v2, 9/15 — 걷기 + 스쿼트)**: 총용량 **394 Nm**(관절마다 굴근·신근 하나씩이면 522, SO 시너지에서 나온 방향이면 521). 걷기가 용량을 정한다(걷기 400, 스쿼트 262 — 스쿼트는 걷기 용량 안에 들어온다). 근육별 용량 25~84 Nm. 한 설계로 7명 12걸음 중 10걸음을 보조 0.8 % 이하로 내고, 나머지 2걸음(5번·10번)은 Moco가 발 접촉 순간에 토크를 잘못 계산하는 노드 때문에 숫자가 크다(v1과 같은 좌표·같은 구간, §13-23). 설계 파일 `report/newmus_V_design_k8.npz`, 그림 `fig_design_directions.png`, 표 `design_directions.csv`. 9/14 v1(걷기 + 스쿼트 + 앉았다 서기 전체)은 `report/archive_v1/`에 있다 — 총용량은 같은 394 Nm였지만 M1·M6·M7 방향이 바뀌었다(코사인 0.27~0.42).

### 10-A. 방향 최적화는 어떻게 했나 (쉽게, 찾아볼 키워드 포함)

**문제를 말로 쓰면.** 새 근육 하나는 "신호 하나로 네 관절에 고정된 비율의 토크를 내는 것"이다. 그 비율이 방향(길이 1인 벡터 4개짜리), 얼마까지 낼 수 있는지가 용량(Nm)이다. 우리가 고를 것은 근육 8개의 방향과 용량. 조건은 "측정된 모든 순간의 관절 토크를, 근육 8개가 각자 0 이상·용량 이하의 신호로 정확히 낼 수 있어야 한다". 목표는 "용량의 합이 가장 작게". 용량 합이 작다 = 액추에이터가 작고 가볍다.

수식으로는 이렇다. 프레임 t의 토크 τ_t (4개 값), 방향 행렬 V (8×4, 각 행 길이 1), 신호 u_t (8개, 0 ≤ u_t ≤ c), 용량 c (8개).

    τ_t = Vᵀ u_t  (모든 t에 대해),   0 ≤ u_t ≤ c,   minimize Σ c_i

**왜 두 단계로 나눴나.** 방향 V와 신호 u를 동시에 고르면 곱셈이 섞여서(Vᵀu) 풀기 어려운 문제가 된다(키워드: **bilinear**, **nonconvex optimization**). 그래서 두 단계로 쪼갰다(키워드: **bilevel optimization**, **alternating optimization**).

- **안쪽 (V를 고정하면)**: 남는 변수는 u와 c뿐이고, 등식·부등식·목표가 전부 일차식이다. 이건 **선형계획법(linear programming, LP)** 이고 정확하고 빠르게 풀린다. 우리는 scipy의 `linprog`, 내부 풀이기 **HiGHS**를 썼다. 변수는 프레임 수 × 8 + 8개. 800프레임이면 0.05초에 풀린다. V가 4차원을 양으로 덮지 못하면(키워드: **positive spanning**, **positive basis**) 해가 없으므로, 못 내는 만큼을 벌점(slack)으로 허용해 항상 답이 나오게 했다.
- **바깥 (V를 바꾸는 것)**: V의 32개 숫자를 조금씩 바꾸며 "안쪽 LP의 답(용량 합)"이 작아지는 방향을 찾는다. 미분을 쓸 수 없는 함수라(안쪽이 LP라 매끄럽지 않음) 미분 없는 방법인 **Powell의 방법**(scipy `minimize(method="Powell")`, 키워드: **derivative-free optimization**, **direction set method**)을 썼다. 각 행을 길이 1로 정규화해서 방향만 바꾼다.
- **여러 번 시작**: 바깥 문제는 국소 최소가 많다(키워드: **local minimum**, **multi-start**). 그래서 5군데서 시작했다: 관절마다 굴근·신근 하나씩(축 정렬), SO 시너지에서 나온 방향(NMF), 무작위 3개. 가장 좋은 답을 고른다. 결과는 시작점에 따라 394~416 Nm로 비슷했다 → 답이 안정적이라는 뜻.

**데이터를 어떻게 넣었나.** 7명의 걷기 42걸음(우리 ID)과 논문 팀이 계산한 스쿼트·앉았다 서기 ID, 좌우 다리를 합쳐 46,006프레임. 사람마다 토크 크기가 다르니 (질량 × 키)로 나눈 뒤 피험자3 값을 곱해 같은 크기로 맞췄다(키워드: **normalization**, **allometric scaling**, 토크 ∝ 체중 × 키). 46,006프레임을 통째로 LP에 넣으면 조건 나쁜 V에서 한 시간 넘게 걸려서, 탐색은 무작위 800프레임(좌표별 최대·최소 프레임은 반드시 포함)으로, 최종 평가는 3,000프레임으로 했다(키워드: **subsampling**, **scenario reduction**). 마지막에 나온 용량으로 46,006프레임 전부를 프레임마다 "0 ≤ u ≤ c인 최소제곱"으로 검산했다(키워드: **bounded least squares**, scipy `lsq_linear`; 상한 없는 버전이 **NNLS, nonnegative least squares**). 못 내는 토크 최대 5.8 Nm.

**결과를 읽는 법.** `newmus_V_design_k8.npz` 안의 `V_nm`(8×4)가 "근육 i를 최대로 켰을 때 네 관절에 생기는 토크(Nm)"다. 행 하나가 근육 하나의 토크 서명(키워드: **torque signature**, **synergy torque vector**). 축 정렬(532 Nm)보다 26 % 적은 이유는 걷기에서 같이 나타나는 토크 조합(예: 밀어차기 때 고관절 굴곡 + 발목 저굴)을 근육 하나가 맡기 때문이다. 이 원리 자체가 사람 이관절근의 존재 이유와 같다(키워드: **biarticular muscle**, **muscle synergy**, **task-space actuation**).

**한계.** 방향은 토크 공간에서만 정했고 아직 어디에 붙는지(경로)가 없다. 다음 단계에서 각 방향을 실제 케이블 경로로 바꾼다(키워드: **moment arm**, **musculoskeletal path**, **wrapping surface**, **cable-driven actuation**). 또 신호 u는 순간마다 자유롭게 고른 것이라, 실제 제어기가 그 신호를 낼 수 있느냐는 별개다(키워드: **feedforward control**, **synergy-based control**).

**"GA(유전 알고리즘)인가?" — 아니다.** 안쪽은 선형계획법(정확한 해), 바깥은 Powell(결정론적 국소 탐색) + 시작점 5개다. GA·CMA-ES·Powell은 모두 "미분 없이 푸는 방법"이지만 성격이 다르다.

| | Powell | CMA-ES | GA |
| --- | --- | --- | --- |
| 방식 | 국소 탐색, 결정론 | 진화 전략: 정규분포로 후보를 뿌리고 분포를 갱신 | 개체군, 교차·돌연변이 |
| 전역성 | 낮음 (multi-start로 보완) | 중간 | 중간~높음 |
| 필요한 평가 횟수 | 적음 (수백~천) | 중간 (수천) | 많음 (수만) |
| 잘 맞는 변수 수 | ~50 | 10~100 | 제한 없음 |

여기서는 평가 한 번이 LP 풀이(0.05초)라 평가 횟수가 비용이어서 Powell을 골랐다. 논문에 방법을 쓸 때는 "LP + Powell (multi-start)"가 정확한 표현이다. 평가가 아주 싼 문제(다음 단계의 경로 설계는 모멘트암을 numpy로 계산하면 마이크로초)에서는 전역 방법(CMA-ES, differential evolution)을 써도 된다.


### 10-B. 지금의 "토크형 근육"에 무엇을 지정했고, 진짜 근육을 만들 땐 무엇을 더 정해야 하나

**토크형 근육 (지금 시뮬레이션에 붙어 있는 것).** OpenSim의 `CoordinateActuator`를 관절 방향마다 하나씩(다리당 4개: 고관절 굴곡, 고관절 내전, 무릎, 발목) 만들고, 그 4개를 `SynergyController`로 묶었다. 지정한 값은 세 가지뿐이다.

| 지정한 것 | 값 | 뜻 |
| --- | --- | --- |
| 어느 관절 방향에 붙나 | 좌표 이름 4개 | 근육이 아니라 "관절에 직접 토크를 넣는 모터" |
| 이득 (`optimal_force`) | 1 Nm | 제어값 1이면 1 Nm |
| 시너지 벡터 8개 | `V_nm`의 각 행 (8×4, Nm) | 신호 u_i 하나가 네 관절에 이 비율로 토크를 냄. 신호 범위 0~1 |

즉 "M2가 켜지면 고관절 굴곡 51, 내전 −17, 무릎 −32, 발목 4 Nm"라는 관계만 있고, 길이·속도·부착점·경로는 없다. 그래서 뷰어에 근육이 안 보인다.

**실제 근육을 만들 때 부착점 외에 지정해야 하는 것.** OpenSim 근육(`Millard2012EquilibriumMuscle`)이나 케이블 액추에이터(`PathActuator`)의 항목과, 우리 인공근육(KIMM 모듈)에 맞게 무엇으로 채울지.

| 항목 | OpenSim 이름 | 사람 근육이면 | 우리 인공근육이면 |
| --- | --- | --- | --- |
| 경로 | path: 시작점·경유점·끝점이 어느 뼈에 붙나 | 해부학 | **설계 방향에 맞게 최적화** (다음 단계) |
| 경로가 뼈를 감싸는 면 | `WrapObject` (원통·구) | 무릎 등 | 무릎·발목에 필요, 케이블이 뼈를 관통하지 않게 |
| 최대 힘 | `max_isometric_force` | 단면적 × 상수 | 모듈 등급의 힘 (초대형 1,000~5,000 N) = 용량 c ÷ 모멘트암 |
| 힘이 나는 길이 범위 | `optimal_fiber_length`, `tendon_slack_length` | 섬유·건 길이 | **스트로크**(변형률 0.40)와 무부하 길이 — 걷는 동안 경로 길이 변화가 스트로크 안에 들어야 함 |
| 힘–길이 곡선 | active/passive force-length | 표준 곡선 | 모듈 실측 힘–변형률 곡선, 수동 강성(변형률 0.10부터, 발산 방지 상한) |
| 힘–속도 곡선 | force-velocity, `max_contraction_velocity` | 표준 | 모듈의 수축 속도 한계 (측정 필요) |
| 켜지는 속도 | activation/deactivation time constants | 10/40 ms | 모듈 응답 시간 (측정 필요) |
| 깃각 | `pennation_angle` | 해부학 | 0 (케이블) |
| 제어 범위 | min/max control | 0~1 | 0~1 |

핵심은 세 가지다. **경로**(모멘트암을 정하고, 곧 방향이 된다), **힘 용량**(모듈 등급), **길이 범위**(스트로크 안에서 걷기의 길이 변화를 감당하나). 나머지 곡선·시간상수는 모듈 측정값이 있으면 넣고, 없으면 케이블 액추에이터(`PathActuator`: 경로 + 힘만)로 먼저 만들어 걷게 한 뒤 채워도 된다. 앞 세 줄이 9/8에 만든 `actuator_model.py`(스트로크 0.40, 수동 강성, 힘밀도 15 N/g)와 연결된다.

### 10-C. 다음 단계 "경로 설계"의 방법과 이름 (찾아볼 키워드)

결정(9/14): 동작 범위 = 걷기 + 스쿼트 + 앉았다 서기(점프 제외), 용량 여유 10 %.

| 단계 | 무엇을 하나 | 기법 이름 / 찾아볼 키워드 |
| --- | --- | --- |
| 모멘트암 계산 | 케이블 길이가 관절 각도에 따라 변하는 비율 −∂L/∂q 이 모멘트암 | **tendon excursion method** (An et al. 1984), **virtual work**; Sherman·Seth·Delp 2013 "What is a moment arm?"; OpenSim `computeMomentArm` |
| 경로 모델링 | 시작·끝점, 경유점, 뼈를 감싸는 면 | **via point**, **wrapping surface**, **obstacle-set method** (Garner & Pandy 2000), **geometric path model** |
| 모멘트암을 자세의 함수로 근사 | 자세마다 계산 대신 다항식으로 | **moment arm polynomial fitting** (van den Bogert; OpenCap 모델 이름의 `_poly`가 이것), **muscle-tendon length surrogate** |
| 모멘트암 행렬 | 케이블 8개 × 관절 4개 행렬 R(q), 토크 = Rᵀ·장력 | 로봇 쪽: **structure matrix**, **tendon Jacobian**; 생체역학: **moment arm matrix** |
| "당기기만 해서 다 낼 수 있나" | 양의 조합으로 토크 공간 덮기 | **force closure**, **wrench closure**, **positive spanning / positive basis**, **tension distribution** (cable-driven parallel robot 문헌) |
| 부착점 최적화 | 부착점·경유점·감싸는 면 반지름을 목적함수로 조정 | **muscle attachment optimization**, **actuator placement optimization**, **tendon routing optimization**, **cable routing optimization** (exosuit 문헌), **musculoskeletal design optimization** |
| 최적화 풀이 | 미분 없는 방법, 시작점 여러 개 | **derivative-free optimization**, **CMA-ES**, **Nelder–Mead**, **Powell**, **multi-start** |
| 스트로크·힘 제약 | 길이 변화 ≤ 스트로크, 용량 ÷ 모멘트암 ≤ 모듈 힘 | **actuator stroke / excursion**, **range of motion**, **force–length**, **wrench-feasible workspace** |
| 검증 | 경로 근육을 달고 걷기 재현 | **MocoInverse**, **static optimization**, **computed muscle control (CMC)**, **tracking simulation** |
| 관련 로봇 | 케이블·인공근육으로 만든 인체형 로봇 | **tendon-driven humanoid**, **musculoskeletal humanoid** (Kenshiro, Roboy), **biarticular actuator**, **cable-driven actuation** |

### 10-D. 경로 설계 결과 (1차 9/14 밤, 2단계 9/15) — 케이블 근육으로 걷고 스쿼트한다

`report/path_design.py`가 두 단계로 돈다.

**1단계 (근육 하나씩)**: 모멘트암 = 케이블 길이의 각도 미분(tendon excursion). 자세 121개(걷기 6걸음 × 10 + 스쿼트 60 + 무릎이 가장 굽은 스쿼트 프레임)에서 모멘트암 벡터가 설계 방향과 나란하도록 부착점을 differential evolution + Powell로 고른다. 비용 = 방향오차(자세 평균 + 최악 자세) + 힘·스트로크·최소 모멘트암 벌점. 근육당 약 20초.

**2단계 (8개 한꺼번에, 9/15 추가)**: 1단계 결과를 출발점으로, 8개 부착점 전부와 힘 배율(≥ 1)을 Powell로 함께 조정한다. 비용 = 표본 프레임 121개에서 "케이블 8개가 신호 0~1로 ID 토크 × 1.1을 재현하고 남는 잔차"(최악 + 0.3 × 평균) + 3 × 방향오차(설계 방향을 유지) + 작은 힘 벌점. 프레임마다 0~1 제약 최소제곱을 벡터화(FISTA)해서 한 번 평가에 5 ms, 전체 90초. 왜 필요했나: 1단계는 근육 하나씩 "방향"만 맞추므로, 깊은 스쿼트(고관절 107°)처럼 모멘트암이 크게 변하는 자세에서 8개를 합쳐도 고관절 토크가 17~28 % 모자랐다(§13-28). 2단계 뒤 표본 프레임 잔차 최악 4.1 %, 스쿼트·걷기 전 프레임 정적 검사 0 %.

| 근육 | 경로 | 설계 방향과 각도차 | 필요 힘 | 스트로크 |
| --- | --- | --- | --- | --- |
| M0~M7 | 6개는 골반→발, M0·M2는 골반→정강이 | 0.6~7.7° | 590~3,460 N | 0.02~0.19 |

전부 KIMM 초대형 모듈(5,000 N) 안, 스트로크(0.40) 안. 힘 배율은 M1만 1.4, 나머지 1.0(설계 용량 그대로). 이 경로 근육(`PathActuator`) 8개를 좌우에 달아 MocoInverse로 재현한 결과(오른다리 케이블 토크 vs ID 최악, ID 피크 대비):

| 피험자3 | walking1 | walking2 | walking3 | TS2 | TS3 | TS4 | 스쿼트 (2.6~4.4 s) | 걷기 전체 구간 (0.03~1.27 s) |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 오차 | 5.5 % | 6.3 | 2.8 | 19.1 (Moco 튐 노드 9개 제외; 포함하면 104) | 3.8 | 4.3 | 9.5 | 12.5 (튐 노드 제외, 무릎) |
| 보조 최악 | 4.8 % | 4.5 | 4.9 | 3.3 | 3.5 | 4.0 | 9.2 | 5.6 |

v1 경로(9/14)와 비교하면 걷기는 6.7 / 5.3 / 7.9 / 23 / 7.9 / 10.1 → 위 표로 전부 좋아졌고, 스쿼트는 5.6 → 9.5 %(v1 스쿼트는 Moco가 수렴 못 한 채 끝난 값, 왼쪽 고관절 보조 22 %; v3는 수렴하고 보조 9 %). "토크 비율 고정" 가정으로 정한 방향이 진짜 케이블(모멘트암이 자세 따라 변함)로도 유지된다는 뜻이다.

**영상**: `report/video_paths_subject3_walking1.mp4`, `report/video_paths_subject3_squats1.mp4` — 뼈대 + 케이블(신호로 진하기) + 지면반력 + 신호 막대 + 토크 추적 + **보조 액추에이터가 떠맡은 토크**(맨 아래 패널, 최악 %가 제목에). **GUI로 보기**: `report/moco/gui_muscles_model.osim`을 열고 `report/moco/gui_paths_subject3_walking1_full_v3.mot` 또는 `gui_paths_subject3_squats1_v3.mot`을 모션으로 — 케이블이 활성도 색으로 칠해진다(§6 GUI 줄). 케이블만 보려면 `report/moco/newmus_paths_subject3_model.osim` + `paths_subject3_walking1_ik_full.mot`. 그림: `report/fig_path_design.png`(방향 vs 모멘트암), `report/fig_path_layout.png`(자세 3개에서의 경로, `report/plot_path_layout.py`).

**남은 한계 (경로 3차에서 고칠 것)**
1. 뼈 간섭을 여전히 안 봤다. 감싸는 면 없이 직선 구간뿐이라 깊은 스쿼트에서 케이블이 뼈를 가로지른다(`fig_path_layout.png` 오른쪽). 관절 중심에서 최소 거리 제약과 wrap cylinder를 넣어야 한다.
2. 8개 중 6개가 골반에서 발까지 4바디를 다 건넌다. 건너는 관절 수에 벌점을 주면 2~3바디 경로가 나온다.
3. 왼다리는 z 부호만 뒤집었고 따로 검증 안 함. 로봇 뼈대 치수가 오면 허용 상자를 바꿔 다시 돌린다.

### 10-E. 다음 단계 (순서대로)

1. **경로 설계 3차** — 만들 수 있는 경로로. 2단계 비용에 관절 중심 최소 거리(3 cm 정도), 무릎·발목 wrap cylinder, 건너는 관절 수 벌점을 더한다. 로봇 뼈대 도면이 오면 허용 상자를 그 치수로 바꿔 다시 돌린다. 하루.
2. **접촉 모델로 스스로 걷기** — 지금은 관절 각도와 지면반력을 사람 것으로 고정해 놓고 토크만 냈다. 발–바닥 접촉 모델을 넣고 각도·지면반력을 고정하지 않은 채(MocoTrack / 예측 시뮬레이션) 8개 근육으로 균형 잡고 걷는지 본다. 지금까지 중 제일 큰 일, 며칠.
3. **인공근육 모듈 측정값 반영** — 힘–속도, 응답 시간, 수동 강성을 `PathActuator` 대신 근육 모델에 넣는다(§10-B 표). 모듈 측정이 필요하다.
4. **제어기** — 지금 신호 u(t)는 최적화기가 순간마다 고른 이상적인 값. 사람 시너지 5개를 feedforward 기본형으로 두고 feedback을 얹는 제어기를 만들어, 그 제어기가 내는 신호로도 걷는지 본다. EMG 시너지 타이밍(§8)이 비교 잣대.
5. 작은 것들: 왼다리 모멘트암 별도 검증, hip_rotation을 5번째 자유도로 넣을지, Moco가 발 접촉 순간에 토크를 잘못 계산하는 노드의 정확한 원인(§13-23).

## 12. 자주 헷갈리는 것 (미리 답)

- **"시너지 5개인데 왜 근육은 8개?"** 5는 사람이 쓰는 제어 패턴 수, 8은 당기기만 하는 근육으로 4방향을 양쪽으로 다 덮는 데 필요한 수. 5개 근육은 무릎을 못 낸다(§5, §6 표).
- **"dual 기준 8개랑 근육 8개는 같은 8?"** 우연. dual의 8은 SO 임의 배분이 만든 숫자, 근육 8은 스패닝에서 나온 숫자.
- **"SO가 EMG랑 다르면 지금까지 결과는 무효?"** 아니다. 관절 토크(ID)는 실측이고 새 근육이 맞춰야 하는 건 그 토크다. SO는 "토크를 어느 근육 묶음으로 보나"에만 관여했고, §10-A에서 그 의존도 없앴다(방향을 ID 토크에서 직접 설계).
- **"Moco 보조 %가 실행마다 다르다"** 보조 가중치 확인(100이어야 함). 1이면 비용 착시.
- **"케이블 경로가 뼈를 뚫고 지나가는데?"** 지금 경로는 힘·스트로크·방향·토크 재현만 목적함수에 넣었고 뼈 간섭은 안 넣었다(§10-D 한계). 목적함수에 없는 조건은 지켜지지 않는다. 3차에서 넣는다.
- **"앉았다 서기는 왜 뺐나?"** 논문 팀 데이터에 의자가 받치는 힘이 없어 앉아 있는 구간의 관절 토크가 틀리다(§13-27). 의자 힘이 없는 구간만 남기면 스쿼트와 같은 동작이라 설계에 새로 보태는 게 없다.
- **"경로 1단계 결과가 정적 검사(NNLS)로는 되는데 왜 2단계가 필요했나?"** 정적 검사는 토크형(방향 고정) 근육으로 한 것이고, 진짜 케이블은 자세마다 모멘트암 방향이 조금씩 다르다. 그 차이가 깊은 스쿼트에서 17~28 %까지 커졌다(§13-28). 2단계는 케이블의 실제 모멘트암으로 8개를 같이 검사하며 조정한다.
- **"최적화가 GA인가?"** 아니다. 방향 설계는 LP + Powell(multi-start), 경로 설계는 differential evolution + Powell. §10-A 표.
- **"walkingTS가 무릎 실험인데 왜 다리 시너지가 같나?"** 몸통만 흔드는 조건이라 다리 근육 패턴은 안 바뀐다. 무릎 내전 모멘트(KAM)는 무릎이 1자유도라 이 모델로 못 잰다.

## 13. 시행착오 기록 — 무엇이 막혔고 어떻게 풀었나

같은 데를 다시 헤매지 않도록 적는다. 각 항목은 "하려던 것 → 잘못된 것 → 어떻게 알았나 → 고친 것 → 배운 것" 순서다.

### 13-1. 환경·데이터 준비

**1. 이전 컴퓨터(Windows)의 작업이 전부 사라졌다.**
남은 건 README와 NOTES 글뿐이었다. 두 문서에 적힌 숫자(잔차 %, 관절 토크 범위, 시너지 수)를 목표로 두고 스크립트를 전부 다시 썼고, 같은 숫자가 나오는지 확인하며 맞췄다. 배운 것: **결과 숫자를 문서에 남겨두면 코드가 없어져도 복구할 수 있다.** 그래서 지금도 README에 결과 표를 계속 갱신한다.

**2. pip가 엉뚱한 파이썬에 설치했다.**
conda 환경 안에서 `pip install`을 했는데 패키지가 안 보였다. 확인해 보니 `pip` 명령이 시스템의 다른 파이썬(3.14)을 가리키고 있었다. 고친 것: 항상 `python -m pip install`로 쓴다.

**3. 어떤 데이터를 쓸지 헷갈렸다.**
구글 드라이브에 비슷한 이름의 폴더가 여럿 있었다(팔 있음/없음, test 붙은 것). 파일을 열어 피험자 수와 안에 든 시행 목록을 세어 보고, 팔이 포함된 `With_Arm` 쪽이 우리가 쓰던 것과 같다는 걸 확인했다. 배운 것: 폴더 이름으로 고르지 말고 **안에 든 피험자·시행 수를 세어서** 고른다.

**4. 잔차 값이 표에 조용히 빠져 있었다.**
.b3d 파일을 읽는 라이브러리(nimblephysics)의 함수가 시행 번호와 처리 단계 번호를 인자로 요구하는데, 인자 없이 불러서 오류가 나고 그 자리에 `-`가 찍히고 있었다. 오류가 화면에 안 나와서 한참 뒤에 알았다. 고친 것: 인자를 넣었다. 배운 것: **표에 `-`가 있으면 "없는 값"이 아니라 "계산 실패"일 수 있다.**

**5. 이전 결과를 덮어쓸 뻔했다.**
새 피험자를 추가하면서 결과 폴더 `out/real`에 그대로 돌렸는데, 요약 파일이 덮어써지는 구조였다. 도중에 멈추고 이전 요약을 백업한 뒤 다시 돌렸다. 배운 것: **결과 폴더에 돌리기 전에 요약 CSV를 날짜 붙여 복사해 둔다.**

**6. 피험자 6·9번을 뺐다.**
이 두 사람은 잔차(계산이 안 맞아 골반에 넣는 가짜 힘)가 기준의 몇 배였다. 처음엔 걸음이 특이한 줄 알았는데, AddBiomechanics가 붙인 "수동 검토 필요" 표시를 보고 데이터 처리 결함이라는 걸 알았다. 배운 것: 잔차가 크면 **사람 탓이 아니라 데이터 탓일 수 있으니** 원본의 표시를 먼저 본다.

### 13-2. 질문을 잘못 읽은 것

**7. "새 근육 k개"를 두 번 잘못 알아들었다.**
"시너지로 새 근육을 만들어 걷게 할 수 있나"를 처음엔 "사람 근육 80개를 신호 k개로 조종하는 것"으로 읽고 그 실험(§6의 A)을 했다. 담당자가 "그게 아니라 아예 새 근육 k개를 만들어 붙이는 것"이라고 두 번 바로잡았다. 그제야 사람 근육을 다 떼고 새 근육을 다는 실험(§6의 B)을 만들었다. 배운 것: A와 B는 다른 질문이다. **A는 "사람 근육을 몇 개 신호로 몰 수 있나", B는 "로봇 근육 몇 개면 되나."** 우리 질문은 B다.

**8. "8개가 안정적이랬는데 5개만 해도 되나?"**
이전 컴퓨터에서 "8"이 나왔던 건 dual 기준(근육 하나하나까지 75 % 설명)이었고, 지금의 "5"는 global 기준(전체 90 %)이다. 둘은 기준이 달라서 다른 숫자가 나온 것이지 결과가 바뀐 게 아니다. 그리고 나중에 하드웨어 검사에서 근육 수로는 8이 필요하다는 게 따로 나왔다(§5). 배운 것: **숫자 앞에 항상 "무슨 기준으로"를 붙인다.**

### 13-3. 시뮬레이션(Moco)에서 막힌 것

**9. 잠긴 관절 때문에 시작도 못 했다.**
AddBiomechanics 모델은 발 내번·발가락·손목 관절을 "잠금" 상태로 둔다. Moco는 잠긴 관절에 액추에이터가 붙어 있으면 거부한다. 고친 것: 그 관절의 액추에이터를 떼고, 관절을 아예 고정(용접)으로 바꿨다. 떼고 나니 손목 액추에이터가 붙을 데 없이 남아서 그것도 먼저 지워야 했다.

**10. 무릎의 종속 좌표가 비어 있었다.**
이 모델의 무릎은 각도 하나로 움직이지만 내부적으로 따라 움직이는 좌표(`knee_angle_beta`)가 하나 더 있다. 받은 IK 파일엔 그게 없어서 Moco가 "좌표가 부족하다"고 했다. 고친 것: 모델 안의 관계식으로 그 좌표를 계산해 IK 파일에 채웠다.

**11. 아주 작은 숫자가 파일을 망가뜨렸다.**
시너지 가중치 중에 0에 가까운 값(10⁻³²⁴ 수준)이 있었는데, 이걸 XML로 저장했다가 다시 읽으면 그 항목이 통째로 비어버렸다. 고친 것: 10⁻⁸보다 작은 값은 0으로 만든다.

**12. 근육 수를 바꿔도 똑같은 오차로 실패했다.**
k를 5, 8, 심지어 30으로 해도 "실행 불가능" 오류의 숫자가 0.833으로 완전히 같았다. 이상해서 찾아보니 OpenSim 근육의 최소 제어값 기본이 0.01인데, 시너지 가중치가 0인 근육은 신호가 항상 0이라 이 최소값을 영원히 못 지키는 것이었다. 고친 것: 최소 제어값을 0으로 두고, 조용한 근육도 빼지 않고 전부 시너지에 넣었다. 배운 것: **k를 바꿔도 결과가 똑같으면 문제는 k가 아니라 설정에 있다.**

**13. 새 근육과 보조가 정확히 반반씩 냈다.**
처음 새 근육 실험에서 보조 액추에이터가 정확히 50 %를 냈다. 너무 깔끔한 숫자라 의심했다. 원인은 새 근육의 출력 토크가 보조와 똑같은 제곱 비용으로 목적함수에 들어가서, 절반씩 나누는 게 최소 비용이 된 것. 고친 것: 새 근육 출력의 비용 가중치를 0으로 두고 신호와 보조에만 비용을 매겼다. 배운 것: **50 %처럼 딱 떨어지는 숫자는 물리가 아니라 수식 구조에서 나온다.**

**14. 결과 신호를 읽는 함수가 안 맞았다.**
Moco 해에서 시너지 신호를 꺼내는 파이썬 함수가 문서와 인자가 달라 계속 오류가 났다. 고친 것: 함수 대신 해를 파일(.sto)로 저장하고 열(column) 이름으로 직접 읽었다.

**15. 파이썬에서 만든 임시 객체를 바로 넘기면 프로그램이 죽었다.**
`처리기 | 필터` 처럼 한 줄로 만들어 넘기면 이유 없이 종료됐다(segfault). 변수에 먼저 담고 `append`로 넣으면 된다. 배운 것: OpenSim 파이썬은 C++ 위에 얇게 얹힌 것이라 **임시 객체를 넘기면 안 된다.**

**16. 보조 비용 가중치 1은 검사가 아니었다.** (§7)
방향을 고정하고 다른 걸음을 걷게 했더니 보조가 22~26 %로 나와 "실패"로 보였다. 그런데 순간순간 힘 균형만 보는 계산으로는 오차가 0이었다. 둘이 다른 이유를 찾으니, Moco 목적함수에서 신호와 보조가 같은 가중치라 신호가 커질 바엔 보조에 떠넘기는 게 싸게 계산됐던 것이다. 보조 가중치를 100으로 올리자 0.4~10 %로 내려왔다. 배운 것: **"보조 %"는 비용 설정에 따라 10배 넘게 바뀐다. 실현 가능성을 물을 땐 보조 가중치를 크게, 그리고 순간 힘 균형 계산과 같이 본다.**

**17. 걸음 하나에서 만든 방향은 다른 걸음에 안 맞았다.** (§7)
walking1에서 뽑은 8개 방향으로 walking2를 내려면 신호가 시너지 피크의 46배까지 필요했다. 무릎을 펴는 방향이 큰 벡터 두 개를 상쇄해서만 나오는 구조였기 때문이다. 여섯 걸음을 합쳐 뽑으니 10배 안으로 들어왔다. 배운 것: **하드웨어 방향은 걸음 하나가 아니라 여러 걸음을 합쳐서 정한다.** 그리고 이게 §10의 "아예 토크에서 직접 최적화"로 이어졌다.

**18. 걸음을 합칠 때 근육 목록이 안 맞았다.**
시너지 계산은 활성도가 아주 낮은 근육을 미리 뺀다(기준 0.05). 걸음마다 빠지는 근육이 달라서 합치면 열 수가 안 맞아 오류가 났다. 고친 것: 합칠 땐 기준을 0으로 두어 근육 목록을 통일했다.

### 13-4. 도구·환경에서 막힌 것

**19. OpenSim 화면(GUI)이 안 열렸다.**
걷는 모습을 보여줘야 하는데 GUI가 안 떴다. 그래서 GUI 없이 관절 각도에서 뼈대를 직접 그려 mp4로 만드는 스크립트를 썼다(`report/newmus_video.py`). ffmpeg도 없어서 `imageio-ffmpeg` 패키지가 들고 오는 실행 파일을 썼다. 부수적으로 GUI보다 낫다: GUI의 체크무늬 바닥은 높이가 틀리게 보인 적이 있는데, 이 영상은 바닥이 정확히 0이다.

**20. 셸 반복문 안에서 여러 걸음을 돌리면 조용히 죽었다.**
Moco를 여러 걸음에 연달아 돌리는 반복문이 3초 만에 아무 결과 없이 끝났다. 하나만 따로 돌리면 됐다. 나중에 원인을 잡았다: 이 Mac의 셸(zsh)은 `$run` 같은 변수를 공백으로 나누지 않아서, `set -- $run`으로 인자를 나누려던 것이 문장 전체가 첫 번째 인자가 되어 스크립트가 잘못된 인자로 실패한 것이었다. `${=run}`으로 쓰면 나뉜다. 배운 것: **여러 개를 돌릴 땐 스크립트 파일 + 로그 파일.** 그림·표에 결과가 비어 있으면 로그부터 본다.

**21. 그래프 글꼴에 한글이 없었다.**
그림에 한글이 네모로 나왔다. 시스템의 Apple SD Gothic Neo 글꼴을 찾아 지정했다. 그림 스크립트마다 같은 코드 몇 줄이 들어 있다.

### 13-5. 결과를 다시 읽게 만든 것

**22. EMG가 SO와 많이 달랐다.** (§8)
실측 근전도를 받아 비교하니 발목·햄스트링은 맞고 대퇴직근·전경골근은 SO가 아예 안 켜고 있었다. 처음엔 "그럼 EMG로 시너지를 다시 뽑아야 하나" 했지만, EMG엔 주요 근육이 빠져 있어 근육 방향을 만들 수 없다. 대신 **근육 방향을 SO 없이 관절 토크에서 직접 정하는 쪽**으로 방향을 바꿨다(§10). 배운 것: 추정치(SO)는 언제든 실측(EMG)에 밀릴 수 있으니, **설계의 기준은 실측에 가까운 값(관절 토크)에 둔다.**

### 13-6. 방향 직접 설계 단계에서 (9/14 저녁)

**23. Moco의 내부 토크가 우리 ID와 다른 순간이 있었다.**
설계한 방향 8개로 7명을 걷게 했더니 5·10번만 왼다리에서 100 % 넘게 실패했다. 부호 규약, 용량, 격자 간격, 필터, 골반 보조 가중치를 하나씩 바꿔 봤지만 숫자가 그대로였다. 결정적이었던 실험은 "용량 무제한인 자유 액추에이터"로 돌려 본 것: 그래도 왼쪽 고관절 토크가 한 순간(0.963~0.983 s) +120 Nm로 튀었다. 운동학을 고정하면 관절 토크는 하나로 정해지므로 이건 설계가 아니라 Moco가 그 순간의 토크를 잘못 계산한 것이다. 시각은 오른발이 바닥에 닿기 시작하는 순간(힘판 힘 0 → 28 N, 압력중심이 (0,0,0)에서 1.5 m 지점으로 점프)과 같았다. 12걸음 중 5걸음에 이런 노드가 있었다. 고친 것: 검증 지표를 "보조가 얼마나 냈나"에서 "새 근육이 낸 토크가 우리 ID와 얼마나 다른가"로 바꾸고, 자유 액추에이터로도 5 Nm 넘게 어긋나는 노드는 뺐다. 배운 것: **검증 도구 자체를 먼저 검증한다.** 자유 액추에이터 실행이 그 방법이다. 보조 %만 봤다면 5·10번을 설계 실패로 잘못 결론냈을 것이다.

**24. 최적화가 끝나지 않는 것처럼 보였다.**
세 번 다시 시작했다. (1) 출력을 필터 명령에 통과시켜서 끝날 때까지 한 줄도 안 보였다 → 100회마다 진행 줄을 찍게 했다. (2) LP 하나에 5초 제한을 걸었더니 전체 46,006프레임 평가(정상도 5.6초)가 전부 실패했다 → 탐색용 표본에만 제한. (3) 조건이 나쁜 방향에서는 전체 프레임 LP가 한 시간 넘게 안 끝났다 → 전체 평가를 3,000프레임 표본으로 바꾸고, 대신 나온 용량으로 모든 프레임을 낼 수 있는지 프레임별로 빠르게 검산했다. 배운 것: **긴 계산은 처음부터 진행 줄과 시간 제한을 넣고, 큰 문제는 표본으로 풀고 전체로 검산한다.**

### 13-7. 경로 설계 단계에서 (9/14 밤)

**25. 목적함수에 없는 조건은 지켜지지 않았다.**
경로 설계 1차는 방향·힘·스트로크만 목적함수에 넣었다. 결과는 세 조건을 다 만족했지만, 그림으로 그려 보니 경유점이 무릎 중심 2 cm 안에 놓이고 스쿼트 자세에서 케이블이 뼈를 가로질렀다. 숫자로는 통과인데 만들 수는 없는 배치다. 배운 것: **최적화 결과는 반드시 그림으로 그려서 눈으로 본다**(`fig_path_layout.png`가 그 역할). 그리고 "뼈를 안 뚫는다" 같은 당연한 조건도 목적함수에 명시해야 한다.

**26. 건너는 관절을 문턱 하나로 정했더니 거의 다 4바디 경로가 됐다.**
방향 성분이 0.12보다 크면 그 관절을 건너게 했는데, 작은 성분(0.13~0.19)까지 건너게 되어 8개 중 7개가 골반→발 경로가 됐다. 만들기는 어렵고 이득은 작다. 2차에서는 건너는 관절 수에 벌점을 주거나 작은 성분은 버리고(문턱 0.25) 그 오차를 다른 근육이 흡수하게 한다.

### 13-8. 설계 v2와 경로 2단계에서 (9/15)

**27. 앉았다 서기 데이터에는 의자가 받치는 힘이 없었다.**
논문 팀의 앉았다 서기(STS) 시행을 설계에 통째로 넣었는데, 힘판 3의 값이 시행 내내 0이고 앉아 있는 동안 발 힘판 합이 체중의 19~36 %뿐이었다. 논문(Uhlrich 2023)도 힘판은 "three in-ground force plates"이고 분석은 "rising phase"만 썼다고 적혀 있다. 즉 앉아 있는 구간의 관절 토크는 의자 힘 없이 계산돼 틀리다. 처음엔 발 힘판 합이 체중의 85 % 이상인 프레임만 남기려 했지만, 그렇게 남는 구간은 스쿼트와 운동학이 같아 새 정보가 없다. 결정: 설계 과제 = 걷기 + 스쿼트. 배운 것: **데이터를 설계에 넣기 전에 측정에 무엇이 빠져 있는지 먼저 본다.** 원문을 직접 확인하고, 힘판 열이 0인지 본다.

**28. 근육 하나씩 방향을 맞춘 경로는 깊은 스쿼트에서 모자랐다.**
새 설계(v2)로 1단계 경로를 다시 만들었더니 걷기는 되는데 스쿼트가 안 됐다(보조 29 %). 방향 설계(토크형) 자체는 스쿼트도 0 % 잔차로 문제없었고, 케이블의 실제 모멘트암으로 정적 검사를 해 보니 고관절 107° 자세에서 고관절 토크가 17 % 모자랐다. 1단계 비용을 "최악 자세 포함"으로 바꿔도 28 %로 더 나빠졌다 — 근육 하나의 방향을 맞추는 것과 8개를 합쳐서 토크를 내는 것은 다른 문제다. 해결: 2단계로 8개 부착점과 힘을 한꺼번에 조정하며 실제 모멘트암으로 토크 재현 잔차를 직접 줄인다(§10-D). 배운 것: **부품 하나씩 맞춘 뒤엔 반드시 전체를 합쳐서 같은 잣대로 검사한다.** 그리고 v1 경로가 스쿼트를 낸 것은 방향이 운 좋게 맞았던 것이지 방법이 보장한 게 아니었다.

**29. 힘에 벌점을 세게 주니 최적화기가 근육의 역할을 바꿔 버렸다.**
2단계 첫 시도에서 힘을 자유 변수로 두고 "힘은 작을수록 좋다"는 벌점을 넣었더니, 잔차는 4 %까지 내려갔다가 힘을 줄이는 쪽으로 가면서 8개 중 6개의 케이블이 설계 방향과 50~140° 다른 곳에 붙었다(잔차 16 %). 숫자상 비용은 내려갔지만 7명 검증과 문서 전체가 기대는 "설계 방향"이 사라진 것이다. 해결: 힘은 "설계 용량 ÷ 최소 모멘트암"에 배율(≥ 1)만 곱하도록 묶고, 방향오차 항을 비용에 남겨 설계 방향을 지키게 했다. 배운 것: **최적화기는 비용에 적힌 대로만 움직인다.** 지키고 싶은 것(여기선 방향)은 비용에 넣어야 하고, 결과는 각도차·힘 표로 반드시 다시 읽는다.
